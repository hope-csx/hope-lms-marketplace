1. Overview & architecture

HOPE MTP 0.2 is one Google Cloud Marketplace Kubernetes application that installs two products into a single namespace of your GKE cluster:

  • The Metahuman Training Platform (MTP) — mtp-web (the learner, author and administrator portal), mtp-api (the control plane and sole database owner), mtp-session-gateway (the WebSocket broker for live sessions), mtp-assessment-engine and mtp-curriculum-engine (Vertex AI inference), and an in-cluster qdrant vector store.
  • The HOPE Metahuman Service it runs on — api, admin-web, agent-engine and a2f3d-engine, plus the optional avatar-bridge for live-video avatar tiers.

Every Service is ClusterIP; you provide DNS, ingress and TLS (section 8). Cloud SQL, Memorystore, Cloud KMS and the NVIDIA Audio2Face-3D NIM are prerequisites in your project (section 2). One offline license unlocks both products (section 3). After install, one manual step connects your training tenant to the bundled HOPE (section 7).

2. Prerequisites in your GCP tenant

  1. GKE cluster (Autopilot or Standard) with Workload Identity and a network-policy-capable dataplane (Dataplane V2).
  2. Cloud SQL for PostgreSQL 16 with two databases — one for MTP, one for HOPE — on one instance or two. Supply each as a connection URL (secrets.databaseUrl, hope.secrets.databaseUrl). The two products must never share a database.
  3. Memorystore for Redis, one instance, shared (global.secrets.redisUrl).
  4. Cloud KMS, HSM-backed, rotation ≤ 90 days. Each product keeps one key per data domain so any one can be rotated or revoked on its own; they may share a key ring.
    • MTP: one ASYMMETRIC_SIGN key version (access tokens) and one ENCRYPT_DECRYPT key (auth data). A second ENCRYPT_DECRYPT key for learner documents is optional.
    • HOPE: two ASYMMETRIC_SIGN key versions (access tokens, workflow signing) and five ENCRYPT_DECRYPT keys (auth data, tool credentials, guardrail data, webhook secrets, conversation data, workflow logs — six keys in total). The HOPE api refuses to start without every one of them.
  5. An SMTP relay for HOPE — host and a sender address it is authorised to send for. HOPE relays invitations and password resets, and refuses to start a production deployment on its logging transport, which would write single-use invitation tokens into the application log. MTP's own mail settings stay optional.
  6. GCP service accounts bound to the Kubernetes ServiceAccounts via Workload Identity: at minimum mtp-api, mtp-assessment-engine, mtp-curriculum-engine, HOPE api and HOPE agent-engine. Grant KMS on the respective keys, roles/aiplatform.user to the two MTP engines and HOPE's agent-engine, Document AI and GCS only where you configure them.
  7. Private Google Access on the subnet so pods reach Google APIs without internet egress.
  8. An SSD-backed StorageClass for the 20 GiB Qdrant volume (qdrant.storageClass).
  9. Two RS256 keypairs for HOPE's service-to-service tokens (section 5, HOPE connection strings) — generate with openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048.
  10. A valid HOPE MTP license (section 3).
  11. (optional avatar tier) a reachable NVIDIA Audio2Face-3D NIM with its own NGC entitlement, and its mTLS certificates.

3. Obtaining & installing your license

Contact CornerstoneX with your organization name and intended term. You receive a single-line signed license blob. Paste it into the global.license.key parameter during deployment; it is stored as the Kubernetes Secrets hope-lms-license (MTP) and hope-metahuman-license (HOPE) and verified offline by both APIs against a public key embedded in their images — no license server is contacted.

Without a valid, unexpired license neither API starts. Both pods enter CrashLoopBackOff and log LICENSE_VALIDATION_FAILED. A license issued for HOPE MTP 0.1 is valid for 0.2.

4. Marketplace deployment (Console flow)

  1. Open the HOPE MTP listing in Google Cloud Marketplace and choose Configure.
  2. Select your cluster and a new namespace. Do not reuse a namespace holding a 0.1.x install (section 11).
  3. Fill in the parameters (section 5). Everything marked Generated is created for you.
  4. Deploy. The install reports ready once every workload is Running and the Qdrant volume is bound; allow up to 25 minutes on a cold cluster.

6. Post-deploy verification

kubectl -n <namespace> get pods
kubectl -n <namespace> get application
kubectl -n <namespace> logs deploy/mtp-api -c api | grep LICENSE_
kubectl -n <namespace> logs deploy/api | grep LICENSE_

Both logs must show LICENSE_VALIDATED. Then browse to your MTP web URL and your HOPE admin URL and sign in as each product's bootstrap application owner.

7. Connect your training tenant to HOPE

The chart deploys HOPE alongside MTP but does not bind a training tenant to it — tenancy in MTP is one HOPE organization per tenant, and that binding is a one-time administrative action:

  1. Sign in to the HOPE admin portal (hope.domains.appUrl) as its application owner and change the bootstrap password.
  2. Create the HOPE organization your training tenant will use, and under it a machine credential (API key) — note its id and secret.
  3. Sign in to the MTP portal (domains.appUrl) as its application owner. Open Platform → Tenants, create (or open) the tenant, and choose Connect to HOPE.
  4. Enter the HOPE organization id, the HOPE API base URL (your public HOPE API URL, hope.domains.jwtIssuer), and the credential id and secret. MTP seals the secret under its KMS key and shows the connection as connected.
  5. Run one training session end to end to confirm the data plane.

9. License lifecycle & operations

Both APIs re-verify the license daily. Within 30 days of expiry they log LICENSE_EXPIRY_WARNING once a day; on expiry they exit and stay down until renewed. To renew, update the global.license.key parameter (or edit both license Secrets) and let the API pods roll.

Marketplace usage labels

Every Pod carries the goog-partner-solution label Google uses to attribute consumption. Do not remove it: mtp-api checks its own label every 15 minutes and serves only /health while it is missing.

10. Troubleshooting

  • API pods in CrashLoopBackOff with LICENSE_VALIDATION_FAILED — the license is missing, altered or expired; re-paste it exactly as issued.
  • migrate init container failing — the database URL is wrong or the database is not reachable from the cluster; the two products must have different databases.
  • Qdrant Pending — the PersistentVolumeClaim did not bind; check qdrant.storageClass exists and can provision a 20 GiB ReadWriteOnce volume.
  • 503 on every MTP route except /health — the goog-partner-solution label was removed from the mtp-api Pod; restore it.
  • Sessions never start — the tenant is not bound to HOPE (section 7) or /ws is not routed to the session gateway (section 8).

11. Upgrading from 0.1.x, uninstalling

0.2 is a new application generation with different images, parameters and resource names. Uninstall a 0.1.x release before installing 0.2 into the same namespace. Uninstalling 0.2 removes every resource except the Qdrant volume claim qdrant-storage, which is kept so an index survives a reinstall; delete it explicitly when you no longer need it.
